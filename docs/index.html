Overview v1.10.0

Your folder, with a team that knows where things are

pka-skills is a Claude Code plugin. Its six skills turn a folder of notes, documents and projects into a personal knowledge system you work with by asking.

Who it is for

You keep meeting notes, 1-1s, research and project folders on your own disk, and you already use Claude Code. You want to ask "what did we decide?" and get an answer, without a new app sitting between you and your files.

The core idea

  • Your files are the source of truth. Every note is a plain file you can open in any editor. PKA reads your existing folders and infers what they mean; it does not impose a structure.
  • Roles do the work. An orchestrator routes what you ask to a librarian (files, OCR, indexing) or a researcher (synthesis).
  • Everything stays in your folder. There is no PKA account, server or sync. The bundled helper makes no network calls and never runs git.

Two things do reach the network. The dashboard, when you have a search index, loads one script (sql.js) from a public CDN. And extracting text from PDFs uses optional Python packages that you install yourself.

Claude Code itself still sends what it reads to its model, as in any Claude Code session. PKA adds nothing to that.

An optional SQLite index speeds up search in a large folder. It is built from the files and can be rebuilt from them at any time.

One folder name has a fixed meaning: knowledge/. PKA calls it the vault. Obsidian support, MOCs and pointer tables (later screens) apply to notes inside it.

  • What can PKA do?
  • How is my knowledge base organized?

Start about five minutes

Install

Two commands inside Claude Code install the plugin and all six skills. Then open Claude Code in the folder that holds your notes.

You need

  • Claude Code.
  • python3 3.9 or newer on your PATH, for the bundled helper. The helper itself needs nothing from pip. If Python is missing or too old, the skills stop and tell you; they do not do the helper's work by hand.
  • No git. Keep the folder in a repository or not, as you prefer.

Optional

  • To make PDFs searchable: pdfplumber or pypdf (Python packages) for PDFs that contain text. tesseract for scans and image-only PDFs. Without them a PDF is still filed, but its contents are not searchable.
  • For the dashboard without an index: Chrome or Edge.
  • For a search index: a Python whose built-in SQLite includes FTS5. The helper tells you if yours does not.
  • Obsidian is not required for anything on this site.

Optional: thinkkit, for meetings

thinkkit is a separate plugin. With it, you type fragments during a meeting and get structured notes, and a transcript can correct those notes before they are filed. Without it, PKA still files notes you wrote yourself.

See Meeting capture for what each looks like.

Skill pka-bootstrap

Set up a workspace

Bootstrap reads the folder you already have, drafts a map of it, asks three questions and writes a small amount of infrastructure around your content.

With the plugin installed and python3 3.9 or newer available, open Claude Code in the folder that holds your notes and say "Set up my PKA".

Before it asks anything, bootstrap scans the folder and infers what each top-level folder contains. The scan skips what .pkaignore lists. That file uses gitignore syntax; the default skips .pka/, .git/, build folders such as node_modules/ and dist/, and everything deeper than one level inside each project. You can edit it.

Three questions

  1. Your name, plus a short profile: what you do and how you like things written. This can add up to two follow-ups, so at most five questions in all.
  2. Autonomy level. See the three levels beside this.
  3. Confirm the map. You correct any folder it was unsure about and confirm where finished projects should be archived.

If you do not use Obsidian, it also offers once to add topic tables to your knowledge folders. That is the pointer layer; you can say no and opt in later.

At the end it shows a schedule entry for a weekly health check. It installs nothing; adding the entry is yours to do.

What it writes

CLAUDE.md, a .pka/ folder and two inboxes. When it adapts to an existing structure it adds infrastructure and does not move your content.

If you already have a CLAUDE.md

Bootstrap asks whether it belongs to an existing PKA or is unrelated. It shows you a diff and waits for your confirmation before overwriting a CLAUDE.md it did not write, whatever autonomy level you chose.

Storage

Under about 300 knowledge files, Claude reads the files directly ("markdown-only"). From 300 up, bootstrap recommends a SQLite index at .pka/knowledge.db. You can override the choice.

Running bootstrap again changes nothing that is already in place. It runs only when you ask for it.

Try this

  • Set up my PKA
  • What autonomy level am I on?

Ask before everything

Every file write, move and delete is confirmed first.

recommended

Ask before destructive actions

Creates and reads go ahead. Moves, overwrites and deletes are confirmed.

Hands-off

It acts and reports afterwards. Press Escape to interrupt.

Asked at every level, including hands-off

  • Ingesting into a topic wiki, or deleting one
  • Approving a project summary before a project is archived
  • Filing a meeting note into an active project
  • Migrating the search index during an upgrade
  • Overwriting a CLAUDE.md PKA did not write

Concept the navigation layer

The Repo Map and CLAUDE.md

A table at the bottom of CLAUDE.md describes every folder. It is the first thing read when you ask where something lives.

Each row says what a folder contains, how it is organized, its priority and status, and how confident the inference was. You correct low-confidence rows at setup.

Tags tell skills where things go

people-home
One subfolder per person. At most one folder has this tag.
meeting-home
Dated meeting notes. pka-meetings routes here.
wiki-home
Topic wikis, one subfolder per topic.
daily-home
A journal of YYYY-MM-DD.md notes. The dashboard shows it as a calendar; in an Obsidian vault these notes get a date and a daily tag.

Project workspaces

A folder with its own CLAUDE.md, such as projects/orion/, is a project workspace: live work with its own context. PKA indexes it only one level deep and never files into it without asking. Project lifecycle covers what happens when the work is done.

Keeping the map current

At the start of each session the orchestrator compares your top-level folders with the map and flags new ones. Archiving a project or creating a wiki updates the row.

To change it yourself, say "Update my repo map". The table is maintained for you and is marked "do not hand-edit".

The rest of CLAUDE.md records your autonomy level, communication style, storage mode, archive destination, and what to do at the start and end of a session. It is plain markdown, so another tool that accepts markdown context can read it too.

Try this

  • Show me my current Repo Map
  • What's in knowledge/leadership/?

Priority

Active and Reference folders are the ones indexed and shown on the dashboard. Archive marks the folder finished projects move into; each archived project gets its own Reference row.

Confidence

Low-confidence rows are the ones bootstrap asks you about before it writes the map.

Concept who does what

Roles and @mentions

Three roles ship with PKA. You can name one with an @mention, or describe what you want and let the orchestrator route it.

@orchestrator
Always active. Routes requests, keeps the Repo Map, runs the session start and end, handles project lifecycle. It answers where things are, and hands file work to the librarian and synthesis to the researcher.
@librarian
Takes files in: inventory, OCR, routing, indexing. Shows a routing proposal before it moves anything, unless you chose hands-off.
@researcher
Synthesizes across your notes. Says what it searched, cites sources, and separates findings from inferences.

Roles and skills are different things

Skills are what the plugin installs. Roles are markdown files that bootstrap writes into your folder, in .pka/roles/. You can read and edit them; roster.md lists them.

Claude Code reads your folder's CLAUDE.md at the start of every session. That file is what makes it act as the orchestrator. The librarian role is carried out by the pka-librarian skill. The researcher has no skill of its own; it also maintains wikis for pka-wiki.

The labels on the conversations in this walkthrough name the role or the skill that is speaking.

Adding a role

Say "Add a data analyst to my team". The researcher writes a competency brief to owner-inbox/research-<role>-<date>.md, a role file is written to .pka/roles/, the roster gains a row, and you are shown the definition to confirm before it is final. A role can have an alias, so a persona name works as an @mention too.

Writing for you

.pka/owner-profile.md holds your communication style. Roles read it. If summaries run long, say so and the profile is updated.

Try this

  • @researcher synthesize <topic>
  • Add a <role> to my team

Skill pka-librarian

The inbox pattern

Two folders, two directions. You drop files into team-inbox/. Reports, briefs and drafts come back to you in owner-inbox/.

Save a PDF, a scan or a document into team-inbox/. The next session notices it, or you can say "Process my team-inbox" now. A scanner profile or a phone's scan-to-folder can point straight at that folder.

For each file the librarian proposes a destination from the Repo Map. Unless you chose hands-off, it waits for your yes before moving anything.

Rules it keeps

  • Originals are never modified. Text extracted from a PDF goes in a sidecar file beside it. The one change it may make is to the name: : and / in a filename are replaced when the file is moved.
  • Nothing is silently skipped. A file with no clear home goes to team-inbox/unsorted/ and is named in the report.
  • Nothing is routed into a project workspace without asking, and nothing is deleted from the inbox without confirmation.

Transcripts wait

A meeting transcript is recognised by its name: a Zoom GMT…transcript.vtt, a Teams …_transcript.docx or .txt, or any .vtt or .srt. It is held, which means it stays in team-inbox/ until you reconcile it with your notes (see Meeting capture) or name a destination for it.

PDFs and scans

Making a PDF searchable needs a tool you install: pdfplumber or pypdf for PDFs that contain text, tesseract for scans. If none is there, the file is still filed, the report says its text could not be read and what to install, and it is not searchable until then.

Try this

  • Process my team-inbox
  • Show me what's in owner-inbox

Concept the most-used capability

Finding things

You ask a question. The orchestrator uses the Repo Map to decide where to look, searches, and answers with the paths it used.

Five kinds of question

  • Simple lookup. "What do I know about Priya?" Works for people, topics, projects and decisions.
  • Search across everything. "Find everything I've written about the Northwind partnership." Results come back ranked and grouped by folder.
  • Project snapshot. "What's the state of Orion?" It reads the project's own CLAUDE.md and top-level documents.
  • Date-scoped. "What did I decide about hiring last quarter?"
  • Decision history. "Why did I archive Lyra?" This reads the decision log, which records the reasons.

What search covers

  • Knowledge folders are indexed in full.
  • Active projects are indexed one level deep: the project's top-level documents, not its subfolders. A project becomes fully searchable once it is archived.
  • PDFs and Office files are searchable through the text sidecar the librarian writes beside them.

Keeping the index current

A note that a skill files is indexed as part of filing. A note you add or edit by hand is not searchable until you say "Re-index my knowledge base". Re-indexing re-reads only changed files, and deleted files drop out.

In a small, markdown-only workspace there is no index; Claude reads the files directly, guided by the Repo Map.

If a topic has a wiki, its summary is shown first. That is covered under Topic wikis.

Try this

  • What do I know about <person>?
  • Find everything I've written about <topic> across all my work

Concept since v1.7.0

People and timelines

A person you keep a folder for has a page, index.md. Filing a note that involves them adds one line to the ## Timeline on that page, newest first.

Who counts as a person

Someone you have a folder for, under the folder tagged people-home (knowledge/personnel/ if none is tagged). PKA does not create person folders unasked: make one, or ask for it.

An attendee without a folder is listed in the note without a link and gets no timeline. With no people folder at all, nothing on this screen happens.

Inside an existing person folder, a missing index.md is created for you the first time a line is added.

Who goes on a note's timeline

Evidence in the note decides, never a guess:

  • the note is in the person's folder;
  • its person or attendees frontmatter (the fields between --- lines at the top of a note), or a link under ## Attendees, names them;
  • their folder name appears in the filename.

A name that appears only in the body does not count. A meeting with more than 8 matched attendees adds none of them unless you ask. no-backref: true in a note's frontmatter keeps it off every timeline.

Names are matched carefully

A full name, a saved alias, or a first name only one person has is a match. A last name alone, or a first name two people share, gets a question. Nicknames are never guessed: tell PKA once and it is saved as an alias.

A line you edit by hand is never rewritten.

Try this

  • File a 1-1 note for <person>
  • From now on, '<nickname>' means <person>

After the first one, open their index.md and look at the Timeline.

Which line came from where

The top line was written when the meeting note was filed, with a summary. The two below were added by a backfill of older notes, which adds no summaries.

Line format

- date · kind · link — summary. Kind is meeting, 1on1 or doc. A summary is at most 140 characters; for a 1-1 it lists topics only.

Links

Relative markdown links, as above. In an Obsidian vault they are wikilinks: [[leadership/2026-11-14-slt-sync|SLT sync]].

Skill pka-meetings with the optional thinkkit plugin

Meeting capture: live notes, and checking them against a transcript

After a meeting, PKA files the notes. With the optional thinkkit plugin it also takes the notes with you during the meeting, and checks them against a transcript afterwards.

Capture live

Say "I'm about to start a 1-1 with Priya" or "take notes". PKA asks what the meeting is and who is attending, then starts thinkkit's take-notes.

  • It creates meeting-notes/YYYY-MM-DD-<title>.md at the workspace root, and first skims earlier notes there for context.
  • You type fragments. Each is expanded into a sentence or two and appended to the file at once, so the file is always current.
  • Start a line with name: to attribute it. Without that it is recorded as an observation; a speaker is never guessed.
  • A commitment is added under Action Items. A question left unanswered goes under Open Questions.
  • You can ask something mid-meeting ("what did we decide about the vendor last month?"). It answers in the conversation and keeps it out of the notes unless you say otherwise. If a fragment is unclear, it asks.
  • Say "end notes" or "done". It tidies the file and tells you how many notes, action items and open questions it captured, and the path.

Reconcile against a transcript

Use this when the meeting was recorded and you have a transcript: a Zoom .vtt, a Teams transcript, an .srt, plain text. Drop it in team-inbox/ and ask.

  • The transcript is treated as the truth. The notes are what get corrected.
  • thinkkit's resolve-against-transcript looks for five things, most serious first: statements that contradict what was said, paraphrases that shift the meaning, wrong speaker attribution, decisions or points missing from the notes, and commitments missing from Action Items. Reasonable compression is not flagged.
  • It shows one discrepancy at a time. You answer accept, modify or skip, and an accepted change is written immediately.
  • It ends with a count of found, resolved and skipped.

If you have a transcript and no notes, PKA offers to generate notes from the transcript.

If you record with earshot

earshot is a separate, local recording and transcription tool. When it is in use, take-notes links the notes to the recording with a **Recording**: line, the reconcile step reads the capture's transcript, and PKA never moves or deletes the capture folder. Only the notes are filed.

Try this, with thinkkit installed

  • I'm about to start a 1-1 with <name>
  • Reconcile my <meeting> notes against the transcript in team-inbox
without thinkkit

Route only

  • Write notes however you like, then say "File these meeting notes: <path>".
  • You get everything on the next screen: routing, attendee links, action items, timelines.
  • No live expansion and no transcript checking. A transcript stays held in team-inbox/, and PKA says which modes are unavailable.
with thinkkit

Capture and reconcile too

  • You type fragments instead of sentences during the meeting.
  • A transcript corrects the notes before they are filed.
  • The plugin also carries unrelated thinking tools, which you can ignore.

The structure is thinkkit's own: the header lines, the three sections, and action items as - [ ] **Owner**: …. The wording of the expanded sentences is illustrative.

Skill pka-meetings

Filing a meeting note, and finding its action items later

However the notes were written, PKA does the same things with them: right folder, attendees linked, action items pulled out, a line on each person's timeline.

What happens to the note

  1. Route. A 1-1 goes to that person's folder, if they have one; otherwise to your general meeting folder, with a suggestion to create one. A leadership or general meeting goes to a meeting-home folder; with several, or none, you are asked.
  2. Link attendees. Each name is checked against your people folders. A certain match is linked under ## Attendees. An ambiguous one is asked about. No match is listed without a link.
  3. Extract action items and ask: "Found N action items. Add to session log open threads?" On a yes they appear in the next session's greeting.
  4. Save. The note leaves meeting-notes/, or wherever you wrote it, and is saved in the destination as YYYY-MM-DD-meeting-slug.md. A 1-1 is YYYY-MM-DD-1-1-<person>.md.
  5. Post-route. The step every filed note gets: a line on each attendee's timeline and the index entry. If your folders have topic tables, a row there too.
  6. Log and report the path, attendees linked (N of M), action items, and what happened to the transcript.

A meeting about an active project always gets a question, at every autonomy level: file it in the project, or in knowledge?

The transcript afterwards

You choose: keep it in team-inbox/ (the default), archive it to a transcripts/ folder beside the note, or delete it after confirming. It is never deleted automatically.

Action items later

"What action items do I have this week?" scans the dated notes in your meeting folders and people folders for unticked - [ ] boxes. It goes by the date in the filename (by default the last 7 days) and lists each item with its source file.

An owner is read from @name and a due date from by YYYY-MM-DD. Tick the box in the note to close an item.

Items captured by thinkkit use a different form (**Owner**: … (due: date)). For now they are listed, but without an owner or due date.

Try this

  • File these meeting notes: <path>
  • What action items do I have this week?

The last item is from a note Sam wrote by hand, in the form PKA reads an owner and a due date from. The first three were captured by thinkkit and are listed as written.

Concept since v1.9.0

Timeline backfill

Timelines start empty and fill in as you file new notes. The backfill puts the notes you already had on them: plan first, apply only when you approve, undo with one command.

  1. Plan. Say "backfill timelines". The librarian works out whose timeline each dated note belongs on, by the same evidence rules as a newly filed note. It writes a report to owner-inbox/ and a plan file under .pka/backfill/. Nothing else changes.
  2. Settle names. The report lists what it could not place: ambiguous names, frequent names with no person folder, notes with no date, large meetings. You confirm an alias or leave it; then it plans again. Planning is cheap.
  3. Apply. Only when you approve. Every page it will touch is backed up to .pka/backups/ first. It adds only lines for notes not already on the timeline, then checks that every link resolves and that nothing else changed. If a check fails, the pages are put back.
  4. Undo if you want to: the apply prints the restore command. It refuses to overwrite a page you edited after the backfill unless you force it.

Your notes are never changed. Only the people's index.md pages are. Backfilled lines have no summaries; ask for them one person at a time.

A note you write by hand later is not on a timeline until a skill files it or you backfill again. A full health check says how many are waiting.

How much it will find

The evidence is the note's folder, its frontmatter, links under ## Attendees, or the filename. A name in the body does not count. For notes written before PKA, that mostly means notes inside a person's folder or with their name in the filename, plus notes linked from old "Mentioned in" or "References" sections on the person's own page. A short plan is not a failure.

How far a timeline reaches

Without Obsidian, a timeline can link to a note anywhere in the workspace, such as projects/ or a meeting folder at the root. The inboxes and hidden folders are left out. In an Obsidian vault (knowledge/), timelines link only inside the vault, because a wikilink cannot leave it.

Try this

  • Backfill the timelines from my old notes
  • Show me what's on <person>'s timeline from <a project folder>

These two lines are the ones without summaries on Priya's page, on the People and timelines screen.

Concept with and without Obsidian

MOCs and the pointer layer

A _MOC.md is a map of content for one knowledge folder. Its ## Pointers table groups files into topics, so a search can land on the topic first and read only the few files in it.

Why, and when

In a large folder, searching note bodies returns a lot of noise. A pointer row is dense with the right words, so it ranks first. A question over 1,500 files becomes a look at a few dozen topic rows, then three to five files read in full.

It starts to pay off once you have hundreds of notes. In a small workspace you can skip this screen.

One row per topic

Three columns: a topic slug, the entities involved, and links to the files. The librarian adds to the table as files are routed. In index mode, pointer rows are indexed with a rank boost over body matches. There is no vector store and there are no embeddings; it is a markdown table.

The librarian names the topic when it can see which one a file belongs to. Otherwise the tool derives one from the note's frontmatter, tags or filename; it never reads the body. A slug gets a year only for a one-off event.

What the librarian will not do

  • Rows are extended, never deleted, reordered or merged.
  • Your edits to a row are kept as you wrote them.
  • A row that reaches 8 files is reported. Splitting it is your call.

If you use Obsidian

You do not need Obsidian for anything on this site. If you use it, the vault has to be the knowledge/ folder: PKA looks for knowledge/.obsidian/, and a vault at the workspace root or elsewhere is not detected.

In a vault, roles add frontmatter, MOC entries and [[wikilinks]] to the files they touch. Existing frontmatter fields are never overwritten.

"bootstrap obsidian" is an optional one-time retrofit: MOC stubs, person indexes and frontmatter derived from filenames and folders. It does not read note bodies and it runs only when you ask.

Try this

  • Set up pointer tables for my knowledge folders
  • bootstrap obsidian

The first is for a workspace without Obsidian; the second needs a vault at knowledge/.

The offsite note in the first row was later deleted. The librarian does not remove pointer links by itself; the health check reports the dead link.

without Obsidian

Opt-in

  • Filing a note never creates a _MOC.md.
  • Rows are written only into MOCs that already exist. Ask for pointer tables to create them: a title and an empty table per folder.
  • Notes get no frontmatter or MOC bullet; links between notes are plain markdown.
with Obsidian

On by default

  • A missing _MOC.md is created when a note is filed.
  • Filed notes get missing frontmatter keys and a bullet under ## Files in the MOC.
  • Links inside the vault are wikilinks.

Skill pka-wiki

Topic wikis

A topic wiki is a maintained summary of what you know about one subject. It cites your notes. It never replaces them.

Two kinds of content

  • Authored moments: your meeting notes, 1-1s, drafts, journal. Records of a specific moment, in your voice.
  • Synthesis pages: topic wikis, kept by the researcher, that change as your understanding does.

Wikis cite moments. Moments never cite wikis. Delete a wiki and you lose no underlying content.

When to make one

When material on a subject is piling up and you want a maintained picture of it. Not for a one-off question, a person or a project; those have their own homes.

Creating one

"Create a topic wiki on MCP" writes an empty scaffold at knowledge/topics/mcp/wiki.md and asks for a first source. The page beside this is what it looks like after two ingests.

Ingest is always reviewed

A wiki changes only when you ingest something; nothing is added automatically. Say "Ingest this paper into my MCP wiki". The researcher reads the source and the current page, sorts what it found into new claims, confirmations, contradictions and refinements, and shows you a section-by-section diff. Nothing is written until you approve, even in hands-off mode. A contradiction is yours to resolve.

A PDF source needs its text sidecar first. A source ingested from team-inbox/ moves to the wiki's sources/ folder.

Asking changes

Once a wiki exists, "what do I know about MCP?" returns the wiki's summary first, then notes that mention the topic and are not in it yet.

Also

"Show me my topic wikis" lists them. "Update my thinking on MCP" edits the "My current thinking" section from what you say. A wiki you are done with can be retired (kept, but left out of answers) or deleted, which always asks first.

Try this

  • Create a topic wiki on <topic>
  • Ingest <path> into my <topic> wiki

Skill pka-interface

The dashboard

A single HTML file, dashboard.html, generated at the root of your workspace for you to open in a browser. No server is set up and there is no build step.

Sections are generated from the Active and Reference folders in your Repo Map. Nothing is hard-coded. Each folder gets the view that suits its content:

Folder holdsView
Per-person notesCard per person, most recent first
Meeting notes (meeting-home)Timeline by date in the filename
Research outputsTopic list with linked files
Journal or lab notesCalendar heatmap and entry list
Project workspacesCard with status and days since activity
Anything elseFile table with search

Two sections are always there: Activity, the last 20 session-log entries, and Search.

Two ways it reads your data

  • With an index: the page reads .pka/knowledge.db in the browser, and search is full-text. To do that it loads the sql.js library from a public CDN, so it makes a network request for that script when it opens.
  • Without an index: it needs Chrome or Edge, and asks you to pick the workspace folder when it opens. Search covers file and folder names only, with a slower "deep search" button for contents.

Keeping it useful

The page reads your data when it opens. Ask for an update after structural changes, such as a new folder in the Repo Map. The skill edits the existing file in place: it rewrites only the sections it generated, which are marked with comments, and leaves what you added outside them alone.

File links are absolute paths on your disk. A dashboard generated in one location has dead links if the workspace moves or is opened on another machine; regenerate it there.

  • Generate my dashboard
  • Add a timeline view for <folder>

Concept handled by pka-bootstrap

Project lifecycle: from active project to archived knowledge

A project folder is a workspace while the work is live. When it is done, a transition moves it into your knowledge base, with a summary, so it turns up in later searches.

PKA mode and project mode

Start Claude Code at the workspace root and you are in PKA mode: everything on this site. Start it inside projects/orion/ and that project's own CLAUDE.md loads instead. PKA is not active there, and bootstrap refuses to run from inside a project. Project work goes on exactly as it did before.

Why archive

An active project is indexed one level deep. After the transition the whole folder is indexed, so a search six months later finds its documents next to everything else.

Noticing

At the start of a session, the orchestrator flags project folders with no file changes in 60 days or more. It only tells you. Nothing is moved.

Transitioning

  1. Summary. A draft is written to owner-inbox/: what it was, key decisions, outcomes, documents worth reading.
  2. Pause. It waits for your approval, whatever your autonomy level.
  3. Cleanup. Build leftovers are listed. You confirm before they are deleted.
  4. Move. The folder goes to your archive destination, and wikilinks that pointed at the old location are rewritten. Anything else that still names the old path is shown to you to fix. The approved summary is copied into the moved folder as project-summary.md.
  5. Re-index and update the map. Status becomes archived, priority Reference.

If the project folder is its own git repository, the move stops and asks first. What happens to that history is your decision.

Changing your mind

"Restore Lyra to active" moves it back and its links follow.

Concept continuity between sessions

The session log and open threads

.pka/session-log.md is a work diary you never write. Each significant action adds one line, and the next session starts from what was left open.

One line, five fields

Date and time, the role, a summary, open threads, and the next action. Every role writes the same form, through one helper command.

The fourth field holds only what is still open. Counts and results go in the summary. That is why the greeting can show things still to do.

What happens when you start a session

  1. Read the open threads of the last 20 entries.
  2. Scan team-inbox/ for new files; flag transcripts.
  3. Compare top-level folders with the Repo Map; flag new ones.
  4. Check projects for 60 or more days of inactivity.
  5. Look at the newest health-check report. If it is at most 7 days old and still has findings, it gets one line. No lint is run.
  6. Greet you with open threads, inbox items and lifecycle flags.

How a thread stops being open

There is no "close" command. The greeting reads the last 20 entries, so an old thread ages out as new entries are written. For an action item, the note is the truth: once its box is ticked (- [x]), the item is closed, even if a log entry still lists it.

Why, not only what

A second file, .pka/decision-log.md, records decisions with their context and the alternatives considered: why a project was archived, why a role was added.

Skill pka-librarian, run by pka-tools lint since v1.10.0

Health checks

Any knowledge base drifts: files move, links rot, the same note is saved twice, a wiki falls behind newer notes. A health check, also called lint, finds these and writes a report. It never edits, moves or deletes anything.

Say "Run a health check". Most of the checks are done by the helper, pka-tools lint, with no model and no network. The result is the same every run and takes seconds.

What each rule finds

RuleFindsQuick
1Things left in team-inbox/unsorted/ and not changed for more than 14 daysyes
2Broken links: a [[wikilink]] or relative markdown link whose file is not there, including links in pointer rowsyes
3A path in a wiki's ## Sources list that no longer existsyes
4A Repo Map row whose folder is missing or holds no documentsyes
5Dated notes that belong on someone's timeline and are not on it. One line of information, not a findingno
6A wiki not updated for 30 days, with 3 or more newer notes on its topic that it does not citeno
7Wiki paragraphs with no citationno
8aFiles that are byte for byte the same, of any typeyes
8bThe same text, once frontmatter, upper and lower case and spacing are set asideyes
8cNear-copies: notes of 200 words or more that are at least 80% alike, or where one holds at least 90% of the other. Often raw notes beside a reconciled version, or a -2 copyno
8dTwo person folders that answer to the same name, or where one folder name is contained in the other; two wikis with the same topic; one topic on two rows of the same pointer tableno

Rules 6 and 7 need judgement. The librarian works them out in a session and appends them to the report the tool wrote. The rest are the tool's.

Quick and full

A full lint is the default. Say "quick lint" for the rules marked above: about a second for a few thousand notes, against a few seconds for a full one. A quick lint run later the same day does not replace a full report.

Reading the report

It lands in owner-inbox/librarian-lint-<date>.md: counts at the top, then a section per rule with a hint about what to do. Every finding ends with an id.

One set of copies is one finding, however many files are in it. Each file is compared with a suggested keeper: the copy with the most links to it, then one that is not in an inbox, then the oldest. It is a starting point; you decide. In the near-copy beside this, the suggestion is the original because a pointer row links to it, while the fuller note is the -2 file.

Acting on a finding

Lint fixes nothing, and neither does the librarian unless you ask, one finding at a time. For a duplicate, say which copy stays: the others are deleted or moved on your yes, and links to a removed copy are rewritten to the keeper.

When a finding is fine as it is

Say "That duplicate is on purpose, hide it". The librarian records the finding's id with your reason in .pka/lint-suppressions.json. It is left out of later reports and counted as suppressed. "What have I hidden from lint?" lists them, and one can be brought back.

An id belongs to the exact files or link it names. If a set of duplicates gains or loses a file, it is a new finding. The line for rule 5 cannot be hidden; a backfill clears it.

Running it every week

Because a quick lint needs no model, it can run unattended. Say "Show me the weekly lint schedule" and you are shown a cron line and a macOS launchd file for Mondays at 09:00. Nothing is installed, by the tool or by any skill: adding the entry is yours to do, and you can ignore it. Setup and upgrades show the same entry.

When the newest report is at most 7 days old and still has findings, the next session's greeting mentions it once. No lint is run at session start.

Try this

  • Run a health check
  • Find duplicate notes
  • That finding is fine, hide it
  • Show me the weekly lint schedule

What these are

  • A note links to a cost sheet that was never filed, and a pointer row still lists a note Sam deleted.
  • knowledge/archive/ is in the Repo Map; nothing is archived yet.
  • Sam wrote a 1-1 note by hand after the backfill.
  • The research brief was copied into Orion.
  • The proposal review was filed twice, the second time with a paragraph added.

Not reported as duplicates

  • A PDF's text sidecar beside its source
  • Anything in an earshot capture directory
  • _MOC.md files, and one topic in two different MOCs
  • What .pkaignore matches
  • Very short notes, such as two files holding only the same headings

Two limits. Near-copy detection compares text, not meaning, so a note rewritten in other words is not found. A scheduled run is a quick lint: it leaves out near-copies, duplicate people and the two wiki rules.

Concept the helper under .pka/bin/

pka-tools: the mechanical half

The skills decide what a note is about and where it belongs. A small Python command makes the edit, the same way every time.

You will rarely type a pka-tools command yourself. The roles run it for the steps that should not depend on a model working them out afresh each session: path arithmetic, table edits, index updates.

  • Python 3.9 or newer, standard library only. Nothing to pip install.
  • No network calls.
  • No git.
  • A copy lives in your workspace at .pka/bin/pka-tools, so a workspace keeps working with the release it was set up on until you upgrade it.

If python3 is missing or older than 3.9, the skills stop and say so. They do not fall back to doing the tool's work by hand.

How it edits your files

  • Only the lines it owns. A pointer row, a tags: line, a line it inserts. Everything else stays byte for byte, line endings included.
  • Never re-renders. Frontmatter is not parsed and written back; tables are not rebuilt or sorted.
  • When unsure, it skips and reports. Malformed frontmatter, a read-only file or an unexpected table is left alone and named.
  • Safe to repeat. Running a command twice changes nothing the second time.
  • Whole writes. A file is written to a temporary name and renamed into place.
  • Its own reports never go through a link. If a lint report's path is a symbolic link, lint stops with one line and writes nothing.

Rule since v1.8.0

PKA never commits

No skill, role or tool stages, commits or pushes, in any repository. Filing a note changes files in your workspace. Committing them is yours to do.

Keep the workspace in one ordinary git repository, or in none. PKA works the same either way, and git is not a requirement.

What this means in practice

  • After a note is filed, the note and every file the filing touched are left in the working tree. The report names them.
  • An upgrade, a backfill or an Obsidian retrofit ends the same way: changes to review, nothing committed.
  • A project folder that is its own repository is never moved without asking you first.

If your workspace is older than v1.8.0

This rule holds for you once you have run the upgrade. The details are on the Upgrading screen.

Skill pka-bootstrap with pka-tutorial

Upgrading, and what's new

Updating the plugin does not change your workspace. Its copy of the helper and its role files stay on the release that set them up until you say "bootstrap upgrade".

Two steps

First update the plugin: in Claude Code, /plugin, then update pka-skills. Then, in the workspace, say "bootstrap upgrade".

What the upgrade does, in order

  1. Helper files. Files you never edited are replaced. A file you edited is kept, with the new version written beside it as <name>.new. In a workspace from before v1.7.0 the tool cannot tell, so it replaces each helper and saves the previous copy. Nothing is deleted: a file the plugin no longer ships is moved to .pka/upgrade-backups/ if you never edited it, and left in place if you did.
  2. The index, if you have one and its schema is older. You are shown a plan and asked. On a yes, the database is copied to .pka/db-backups/, migrated and checked; a failure rolls back.
  3. Role files. .pka/roles/ is backed up. New sections are added. Sections you already have are not rewritten. Sections an earlier release wrote and you never edited can be refreshed in one step, if you say yes.

Throughout: your notes are not touched (the upgrade changes .pka/ only), nothing is committed, and it needs python3 3.9 or newer.

A preview first

Ask the tutorial "Do I need to upgrade?" It compares your workspace with the installed release, shows a preview that changes no file, explains each step, and hands over to pka-bootstrap when you are ready. Afterwards it teaches what is new, using your own folder names.

The upgrade ends by showing the weekly health-check schedule entry, which you can install or ignore. If the workspace was on a release before v1.9.0, the next step is the timeline backfill.

If an earlier release committed for you

Releases v1.6.0 to v1.7.0 could set a workspace up with nested repositories and commit into them after each filed note. That was removed in v1.8.0. Your repositories and their history are untouched.

  • Until you run "bootstrap upgrade", the old helper in your workspace behaves as its own release did, which means it still commits.
  • The upgrade lists the commit and push sections of your role files as obsolete. The ones you never edited are removed when you accept the refresh; edited ones are left for you. Until they are gone, they still tell the roles to commit and push.
  • After that, filing a note in a workspace that still has that layout ends with a "not committed" line as a reminder.

Where the backups are

.pka/upgrade-backups/<timestamp>/ for helper and role files; .pka/db-backups/ for the index.

Skill pka-tutorial

The guided tour, in your own workspace

This site uses a fictional workspace. pka-tutorial covers the same ground inside yours, in eleven modules, with your folder names and prompts you can try as you go.

Say "Give me a tour", or ask how to do one thing. The skill first works out where you are:

  • Not set up yet: it points you to pka-bootstrap.
  • Workspace behind the installed release: it offers the upgrade walkthrough first, because some of what it would show does not work until then.
  • Up to date: the full tour, or any single module.

How it teaches

  • One idea, one example prompt, then "want to try it?"
  • It hands off instead of acting. It never moves or deletes files, and it does not perform the upgrade.
  • Ask a real question in the middle and it stops teaching and answers.

What depends on your workspace

Two modules are taught in full only where they apply: people and timelines when you have a people folder, and the pointer layer when you use Obsidian or have opted in to pointer tables. Otherwise the tutorial says briefly what they are and how to get them.

Upgrading is not a module. The tutorial checks your workspace first and, when it is behind, walks you through the upgrade and then teaches what is new.
