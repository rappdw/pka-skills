Overview v1.9.0

Your folder, with a team that knows where things are

pka-skills is a Claude Code plugin. Its six skills turn a folder of notes, documents and projects into a personal knowledge system you work with by asking.

Who it is for

You keep meeting notes, 1-1s, research and project folders on your own disk, and you already use Claude Code. You want to ask "what did we decide?" and get an answer, without a new app sitting between you and your files.

The core idea

  • Your files are the source of truth. Every note is a plain file you can open in any editor. PKA reads your existing folders and infers what they mean; it does not impose a structure.
  • Roles do the work. An orchestrator routes what you ask to a librarian (files, OCR, indexing) or a researcher (synthesis).
  • Everything stays in your folder. There is no PKA account, server or sync. The bundled helper makes no network calls and never runs git.

An optional SQLite index speeds up search in a large folder. It is built from the files and can be rebuilt from them at any time.

Claude Code itself still sends what it reads to its model, as in any Claude Code session. PKA adds nothing to that.

Skill pka-bootstrap

Set up a workspace

Bootstrap reads the folder you already have, drafts a map of it, asks three questions and writes a small amount of infrastructure around your content.

Open Claude Code in the folder that holds your notes and say "Set up my PKA". Before it asks anything, bootstrap scans the folder (skipping whatever .pkaignore lists) and infers what each top-level folder contains.

Three questions

  1. Your name, plus a short profile: what you do and how you like things written.
  2. Autonomy level. Ask before everything; ask before destructive actions (recommended); or hands-off.
  3. Confirm the map. You correct any folder it was unsure about and confirm where finished projects should be archived.

What it writes

CLAUDE.md, a .pka/ folder and two inboxes. When it adapts to an existing structure it adds infrastructure and does not move your content.

Storage is chosen by size. Under about 300 knowledge files, Claude reads the files directly ("markdown-only"). From 300 up, bootstrap recommends a SQLite index at .pka/knowledge.db. You can override the choice.

Running bootstrap again changes nothing that is already in place. It runs only when you ask for it.

  • Set up my PKA
  • What autonomy level am I on?

Concept the navigation layer

The Repo Map and CLAUDE.md

A table at the bottom of CLAUDE.md describes every folder. It is the first thing read when you ask where something lives.

Each row says what a folder contains, how it is organized, its priority and status, and how confident the inference was. You correct low-confidence rows once, at setup.

Tags tell skills where things go

people-home
One subfolder per person. At most one folder has this tag.
meeting-home
Dated meeting notes. pka-meetings routes here.
wiki-home
Topic wikis, one subfolder per topic.
daily-home
A journal of YYYY-MM-DD.md notes.

The map is kept current

At the start of each session the orchestrator compares your top-level folders with the map and flags new ones. Archiving a project or creating a wiki updates the row.

The rest of CLAUDE.md records your autonomy level, communication style, storage mode, archive destination, and what to do at the start and end of a session. It is plain markdown, so another tool that accepts markdown context can read it too.

Try this

  • Show me my current Repo Map
  • What's in knowledge/leadership/?

Priority

Active and Reference folders are the ones indexed and shown on the dashboard. A finished project becomes Reference when it is archived.

Confidence

Low-confidence rows are the ones bootstrap asks you about before it writes the map.

Concept who does what

Roles and @mentions

Three roles ship with PKA. You can name one with an @mention, or describe what you want and let the orchestrator route it.

@orchestrator
Always active. Routes requests, keeps the Repo Map, runs the session start and end, handles project lifecycle. It delegates knowledge work and reports the result.
@librarian
Takes files in: inventory, OCR, routing, indexing. Shows a routing proposal before it moves anything.
@researcher
Synthesizes across your notes. Says what it searched, cites sources, and separates findings from inferences.

Each role is a markdown file in .pka/roles/ that you can read and edit. roster.md lists them.

Adding a role

Ask for one. The researcher writes a competency brief to owner-inbox/, a role file is written to .pka/roles/, and you are shown the definition to confirm before it is final.

Writing for you

.pka/owner-profile.md holds your communication style. Roles read it. If summaries run long, say so and the profile is updated.

Try this

  • Show me my role roster
  • @researcher synthesize <topic>

Skill pka-librarian

The inbox pattern

Two folders, two directions. You drop files into team-inbox/. Reports, briefs and drafts come back to you in owner-inbox/.

Save a PDF, a scan or a document into team-inbox/. The next session notices it, or you can say "Process my team-inbox" now.

For each file the librarian proposes a destination from the Repo Map. Unless you chose hands-off, it waits for your yes before moving anything.

Rules it keeps

  • Originals are never modified. Text extracted from a PDF goes in a sidecar file beside it.
  • Nothing is silently skipped. A file with no clear home goes to team-inbox/unsorted/ and is named in the report.
  • Transcripts (.vtt, .srt) are held for pka-meetings, so raw transcript text is not filed before it is reconciled with your notes.
  • Nothing is routed into a project workspace without asking, and nothing is deleted from the inbox without confirmation.

If no OCR tool is installed, the librarian says which files it could not read and what to install. It does not pretend they were processed.

Try this

  • Process my team-inbox
  • Show me what's in owner-inbox

Concept the most-used capability

Finding things

You ask a question. The orchestrator uses the Repo Map to decide where to look, searches, and answers with the paths it used.

Four kinds of question

  • Simple lookup. "What do I know about Priya?" Works for people, topics, projects and decisions.
  • Search across everything. "Find everything I've written about the Northwind partnership." Results come back ranked and grouped by folder, with project folders included if you want them.
  • Project snapshot. "What's the state of Orion?" It reads the project's own CLAUDE.md and top-level documents.
  • Date-scoped. "What did I decide about hiring last quarter?"

How the search runs

In index mode the roles call one command, pka-tools search, so search behaves the same in every session. Only changed files are re-read when the index is refreshed, and deleted files drop out.

In a small, markdown-only workspace there is no index; Claude reads the files directly, guided by the Repo Map.

If a topic has a wiki, its summary is shown first. That is covered under Topic wikis.

Try this

  • What do I know about <person>?
  • Find everything I've written about <topic> across all my work

Skill pka-meetings

Meeting capture and its three modes

Capture live, reconcile against a transcript, or file notes you already wrote. All three end in the same filing steps.

Capture and reconciliation are done by two skills from a separate plugin, thinkkit. PKA does the routing, linking, indexing and logging. Without thinkkit, route-only mode still works.

After any mode

  1. Route. A 1-1 goes to that person's folder. A leadership or general meeting goes to a meeting-home folder. For a meeting about an active project, you are asked whether it belongs in the project or in knowledge.
  2. Link attendees. Each name is checked against your people folders. A certain match is linked. An ambiguous one is asked about. No match is listed without a link.
  3. Extract action items into one ## Action Items section.
  4. Save as YYYY-MM-DD-meeting-slug.md. A 1-1 is YYYY-MM-DD-1-1-<person>.md.
  5. Post-route. The step every filed note gets: a line on each attendee's timeline, the index entry, and, where your workspace has them, a pointer row, frontmatter and a MOC link.
  6. Log and report what was filed where.

You are always asked what to do with a transcript afterwards. It is never deleted automatically.

Try this

  • I'm about to start a 1-1 with <name>
  • File these meeting notes: <path>

Concept since v1.7.0

People and timelines

Each person has a folder with an index.md. Filing a note that involves them adds one line to the ## Timeline on that page, newest first.

A person is a subfolder of the folder tagged people-home. Their page becomes a hub: one line per meeting, 1-1 or document, each with a link and a short summary of what was decided and what they own.

Who goes on a note's timeline

Evidence in the note decides, never a guess:

  • the note is in the person's folder;
  • its person or attendees frontmatter, or a link under ## Attendees, names them;
  • their folder name appears in the filename.

A name that appears only in the body does not count. A meeting with more than 8 matched attendees adds none of them unless you ask. no-backref: true in a note's frontmatter keeps it off every timeline.

Names are matched carefully

A full name, a saved alias, or a first name only one person has is a match. A last name alone, or a first name two people share, gets a question. Nicknames are never guessed: tell PKA once and it is saved as an alias.

A line you edit by hand is never rewritten.

Try this

  • File a 1-1 note for <person>
  • From now on, '<nickname>' means <person>

After the first one, open their index.md and look at the Timeline.

Line format

- date · kind · link — summary. Kind is meeting, 1on1 or doc. The summary is at most 140 characters; for a 1-1 it lists topics only.

Links

Relative markdown links, as above. In an Obsidian vault they are wikilinks: [[leadership/2026-11-14-slt-sync|SLT sync]].

Concept new in v1.9.0

Timeline backfill

Timelines fill in as you file new notes. The backfill puts the notes you already had on them: plan first, apply only when you approve, undo with one command.

  1. Plan. Say "backfill timelines". The librarian works out whose timeline each dated note belongs on, by the same evidence rules as a newly filed note, and writes a report to owner-inbox/. Nothing else changes.
  2. Settle names. The report lists what it could not place: ambiguous names, frequent names with no person folder, notes with no date, large meetings. You confirm an alias or leave it; then it plans again. Planning is cheap.
  3. Apply. Only when you approve. Every page it will touch is backed up to .pka/backups/ first. It adds only lines for notes not already on the timeline, then checks that every link resolves and that nothing else changed. If a check fails, the pages are put back.
  4. Undo if you want to: the apply prints the restore command.

Your notes are never changed. Only the people's index.md pages are. Backfilled lines have no summaries; ask for them one person at a time.

How far a timeline reaches

Without Obsidian, a timeline can link to a note anywhere in the workspace, such as projects/ or a meeting folder at the root. The inboxes and hidden folders are left out. In an Obsidian vault, timelines link only inside the vault, because a wikilink cannot leave it.

Try this

  • Backfill the timelines from my old notes
  • Show me what's on <person>'s timeline from <a project folder>

Concept with and without Obsidian

MOCs and the pointer layer

A _MOC.md is a map of content for one knowledge folder. Its ## Pointers table groups files into concept clusters, so a search can land on the cluster first and read only the few files in it.

One row per cluster

Three columns: a topic slug, the entities involved, and links to the files. The librarian adds to the table as files are routed. Pointer rows are indexed with a rank boost over body matches, so they come up first. There is no vector store and there are no embeddings; it is a markdown table.

What the librarian will not do

  • Rows are extended, never deleted, reordered or merged.
  • Your edits to a row are kept as you wrote them.
  • A row that reaches 8 files is reported. Splitting it is your call.

If you use Obsidian

PKA treats knowledge/ as the vault when knowledge/.obsidian/ exists. Roles then add frontmatter, MOC entries and [[wikilinks]] to the files they touch. Existing frontmatter fields are never overwritten.

"bootstrap obsidian" is an optional one-time retrofit: MOC stubs, person indexes and frontmatter derived from filenames and folders. It does not read note bodies and it runs only when you ask.

Try this

  • Set up pointer tables for my knowledge folders
  • bootstrap obsidian

The first is for a workspace without Obsidian; the second needs a vault at knowledge/.

with Obsidian

On by default

  • A missing _MOC.md is created when a note is filed.
  • Filed notes get missing frontmatter keys and a bullet under ## Files.
  • Links inside the vault are wikilinks.
without Obsidian

Opt-in

  • Filing a note never creates a _MOC.md.
  • Rows are written only into MOCs that already exist. Ask for pointer tables to create them.
  • Notes get no frontmatter or MOC bullet; links are plain markdown.

Skill pka-wiki

Topic wikis

A topic wiki is a maintained summary of what you know about one subject. It cites your notes. It never replaces them.

Two kinds of content

  • Authored moments: your meeting notes, 1-1s, drafts, journal. Records of a specific moment, in your voice.
  • Synthesis pages: topic wikis, kept by the researcher, that change as your understanding does.

Wikis cite moments. Moments never cite wikis. Delete a wiki and you lose no underlying content.

When to make one

When material on a subject is piling up and you want a maintained picture of it. Not for a one-off question, a person or a project; those have their own homes.

Ingest is always reviewed

Say "Ingest this paper into my MCP wiki". The researcher reads the source and the current page, sorts what it found into new claims, confirmations, contradictions and refinements, and shows you a section-by-section diff. Nothing is written until you approve, even in hands-off mode. A contradiction is yours to resolve.

Asking changes

Once a wiki exists, "what do I know about MCP?" returns the wiki's summary first, then notes that mention the topic and are not in it yet.

Try this

  • Create a topic wiki on <topic>
  • Ingest <path> into my <topic> wiki

Skill pka-interface

The dashboard

One HTML file at the root of your workspace. No server and no build step: double-click dashboard.html and it opens in your browser.

Sections are generated from the Active and Reference folders in your Repo Map. Nothing is hard-coded. Each folder gets the view that suits its content:

Folder holdsView
Per-person notesCard per person, most recent first
Meeting notes (meeting-home)Timeline by date in the filename
Research outputsTopic list with linked files
Journal or lab notesCalendar heatmap and entry list
Project workspacesCard with status and days since activity
Anything elseFile table with search

Two sections are always there: Activity, the last 20 session-log entries, and Search.

Updating it

Say what you want added or changed. The skill edits the existing file in place and leaves your customizations alone.

Two ways it reads your data

With an index, the page reads .pka/knowledge.db in the browser. To do that it loads the sql.js library from a public CDN, so the page makes a network request for that script when it opens. Without an index, it reads the folder through the browser's File System Access API, which needs Chrome or Edge.

  • Generate my dashboard
  • Add a timeline view for <folder>

Concept handled by pka-bootstrap

Project lifecycle: from active project to archived knowledge

A project folder is a workspace while the work is live. When it is done, a transition moves it into your knowledge base, with a summary, so it turns up in later searches.

Noticing

At the start of a session, the orchestrator flags project folders with no file changes in 60 days or more. It only tells you. Nothing is moved.

Transitioning

  1. Summary. A draft project-summary.md is written to owner-inbox/: what it was, key decisions, outcomes, documents worth reading.
  2. Pause. It waits for your approval, whatever your autonomy level.
  3. Cleanup. Build leftovers are listed. You confirm before they are deleted.
  4. Move. The folder goes to your archive destination, and wikilinks that pointed at the old location are rewritten. Anything else that still names the old path is shown to you to fix.
  5. Re-index and update the map. Status becomes archived, priority Reference.

If the project folder is its own git repository, the move stops and asks first. What happens to that history is your decision.

Changing your mind

"Restore Orion to active" moves it back and its links follow.

Try this

  • What projects are winding down?
  • Transition <project> to knowledge

Concept continuity between sessions

The session log and open threads

.pka/session-log.md is a work diary you never write. Each significant action adds one line, and the next session starts from what was left open.

One line, five fields

Date and time, the role, a summary, open threads, and the next action. Every role writes the same form, through one helper command.

The fourth field holds only what is still open. Counts and results go in the summary. That is why the greeting can show things still to do.

What happens when you start a session

  1. Read the open threads of the last 20 entries.
  2. Scan team-inbox/ for new files; flag transcripts.
  3. Compare top-level folders with the Repo Map; flag new ones.
  4. Check projects for 60 or more days of inactivity.
  5. Greet you with open threads, inbox items and lifecycle flags.

Why, not only what

A second file, .pka/decision-log.md, records decisions with their context and the alternatives considered: why a project was archived, why a role was added.

Try this

  • What did I leave open last time?
  • What action items are still open from the last two weeks?

Skill pka-librarian

Health checks

Any knowledge base drifts: files move, links rot, a wiki falls behind newer notes. A health check finds these and writes a report. It never fixes anything on its own.

What it looks for

CheckFlags
Orphan filesFiles in team-inbox/unsorted/ for more than 14 days
Broken linksMarkdown links and [[wikilinks]] pointing nowhere, including links in pointer rows
Stale wiki sourcesA wiki citing a file that no longer exists
Empty foldersRepo Map folders with no content
Missing back-referencesA note mentions someone whose folder does not link back (low priority)
Contradiction candidatesA wiki with several newer notes on its topic not yet ingested
Uncited wiki claimsWiki paragraphs with no citation

The first four are plain file checks and run quickly; ask for a "quick lint" to run only those. The default runs all seven.

When to run it

Weekly or monthly, and after a large import or a reorganization. Not every session.

The report lands in owner-inbox/ with a summary on top, details below and suggested next actions at the end. You act on it; the check does not modify files.

  • Run a health check
  • Check for broken links

Concept the helper under .pka/bin/

pka-tools: the mechanical half

The skills decide what a note is about and where it belongs. A small Python command makes the edit, the same way every time.

You will rarely type a pka-tools command yourself. The roles run it for the steps that should not depend on a model working them out afresh each session: path arithmetic, table edits, index updates.

  • Python 3.9 or newer, standard library only. Nothing to pip install.
  • No network calls.
  • No git.
  • A copy lives in your workspace at .pka/bin/pka-tools, so a workspace keeps working with the release it was set up on until you upgrade it.

How it edits your files

  • Only the lines it owns. A pointer row, a tags: line, a line it inserts. Everything else stays byte for byte, line endings included.
  • Never re-renders. Frontmatter is not parsed and written back; tables are not rebuilt or sorted.
  • When unsure, it skips and reports. Malformed frontmatter, a read-only file or an unexpected table is left alone and named.
  • Safe to repeat. Running a command twice changes nothing the second time.
  • Whole writes. A file is written to a temporary name and renamed into place.

Try this

  • Re-index my knowledge base
  • File this meeting note

After the second, read the summary: it lists each step and what it did.

Rule since v1.8.0

PKA never commits

No skill, role or tool stages, commits or pushes, in any repository. Filing a note changes files in your workspace. Committing them is yours to do.

Keep the workspace in one ordinary git repository, or in none. PKA works the same either way, and git is not a requirement.

What this means in practice

  • After a note is filed, the note and every file the filing touched are left in the working tree. The report names them.
  • An upgrade, a backfill or an Obsidian retrofit ends the same way: changes to review, nothing committed.
  • A project folder that is its own repository is never moved without asking you first.

If you set up a workspace before v1.8.0

Earlier releases could commit for you after each filed note. That was removed. Your repositories and their history are untouched; PKA no longer commits or pushes in them. The filing summary reminds you with a "not committed" line.

Try this

  • File this note

Then run git status yourself in the folder it went to.

PKA does
  • Moves and writes files
  • Updates timelines, pointer rows and the index
  • Tells you which files changed
You do
  • Review the changes
  • Stage and commit, if you use git
  • Push, when and where you choose

Skill pka-bootstrap with pka-tutorial

Upgrading, and what's new

Updating the plugin does not change your workspace. Its copy of the helper and its role files stay on the release that set them up until you say "bootstrap upgrade".

What the upgrade does, in order

  1. Helper files. Files you never edited are replaced. A file you edited is kept, with the new version written beside it as <name>.new. In a workspace from before v1.7.0 the tool cannot tell, so it replaces each helper and saves the previous copy. Nothing is deleted: a file the plugin no longer ships is moved to .pka/upgrade-backups/ if you never edited it, and left in place if you did.
  2. The index, if you have one and its schema is older. You are shown a plan and asked. On a yes, the database is copied to .pka/db-backups/, migrated and checked; a failure rolls back.
  3. Role files. .pka/roles/ is backed up. New sections are added. Sections you already have are not rewritten. Sections an earlier release wrote and you never edited can be refreshed in one step, if you say yes.

Throughout: your notes are not touched (the upgrade changes .pka/ only), nothing is committed, and it needs python3 3.9 or newer.

A preview first

Ask the tutorial "Do I need to upgrade?" It compares your workspace with the installed release, shows a preview that changes no file, explains each step, and hands over to pka-bootstrap when you are ready. Afterwards it teaches what is new, using your own folder names.

Try this

  • Do I need to upgrade?
  • What's new in this release?

Where the backups are

.pka/upgrade-backups/<timestamp>/ for helper and role files; .pka/db-backups/ for the index.

More than one machine

Each needs the plugin updated. The index is per machine, so each migrates its own.

Skill pka-tutorial

The guided tour, in your own workspace

This site uses a fictional workspace. pka-tutorial covers the same ground inside yours, with your folder names and prompts you can try as you go.

Say "Give me a tour", or ask how to do one thing. The skill first works out where you are:

  • Not set up yet: it points you to pka-bootstrap.
  • Workspace behind the installed release: it offers the upgrade walkthrough first, because some of what it would show does not work until then.
  • Up to date: the full tour, or any single module.

How it teaches

  • One idea, one example prompt, then "want to try it?"
  • It hands off instead of acting. It never moves or deletes files, and it does not perform the upgrade.
  • Ask a real question in the middle and it stops teaching and answers.

Each module takes two to four minutes of reading.
